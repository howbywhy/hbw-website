# Where the lag came from, and what is left

Everything below was measured on this Mac, in Chrome, with a real GPU at the
2× scale of the screen, scrolling each page for about four seconds. That
matters more than it sounds: **every measurement I took headless said the site
was fine.** It was not. Headless Chrome rasterises in software and skips most
of what makes a page feel slow, so it reported a clean 17ms frame on pages that
were dropping one frame in five. Two rounds of fixes went to the wrong things
because of it. Nothing in this document comes from a headless run.

The unit throughout is the gap between frames. This screen runs at 120Hz, so
8.3ms is perfect and anything over 33ms is a visible stutter.

## Where it ended up

Scrolling, frames dropped per ~450:

| | before | now |
|---|---|---|
| Front page | 1/380 | 1/394 |
| Made by Madelen | **71/379** | 1/476 |
| KOJA | 1/455 | 1/457 |
| SUB:3 | 1/467 | 1/431 |

Worst single frame on a project page: **324ms → 40ms.** p99: **129.6ms → 10.4ms.**

The front page was never the problem. It has always been smooth. Every
complaint was a project page.

## The four causes, largest first

**1. A full-window blur running on every frame, forever.** The gallery's panel
carried `backdrop-filter: blur(34px)` across the whole window, set inline with
a note saying it "never changes" — which also meant it never stopped. A project
page *is* the gallery, so on every frame the compositor read back the viewport
and blurred it with a 34px kernel: 5 megapixels on this screen, 11 while a
frame was full bleed and a second blur stacked on top. Behind it sat the work
line, which scrolls, so the result could never be cached. Three more full-window
blurs were doing the same at smaller radii, including the one rule every
overlay shares.

All four are flat ground now, carried heavier to replace what the blur was
hiding. Blur per frame: **1.50 megapixels → 0.21** in gallery view, **2.74 →
0.14** at full bleed. What is left is the chrome, 24 pixels tall.

**2. Every frame of a project rendered its picture at full size.** The flag
deciding this said `true`, with a comment worrying that pages without pictures
would collapse the rail — they do not, because each page already carries its
own width from the frame's dimensions. That put 2.5 megapixels of drawn media
in the band, 10 at 2× scale, re-rastered and re-uploaded as it moved. The trace
named it exactly: **643ms of `IOSurfaceImageBacking::WaitForCommandsToBeScheduled`
in three seconds** — the GPU waiting on texture uploads. The band keeps a window
of six either side now; the grid keeps everything, because its thumbnails are
small.

**3. Pictures asked for two to three times the size they were drawn at.** One
`sizes` figure covered every frame in the band and said 46vw — 662 pixels on
this laptop — while a portrait is drawn at 240. The browser believed it and
decoded a 1440-wide rendition into a 240-wide slot, and those decodes are
16–26ms tasks landing mid-scroll. A band frame is as wide as its picture is at
the height of the window, which is `75vh × its own aspect`, so that is what each
one now asks for.

Separately, the sequence API had been handing the browser 22 frames at whatever
size the CMS held them — a 1920-wide still for a cell 180 across. Its own
comment claimed it built "the same shape the project's own page builds"; it
built a copy. It calls the one builder now.

**4. Up to five films decoding at once.** The band played two frames either
side. Pausing every video took Made by Madelen from 19 dropped frames in 427 to
1 in 450 — the whole of what remained. One film runs now, the one you are on.

Worth recording: **KOJA has nineteen films and they cost nothing measurable.**
This is about what the files are, not how many — Made by Madelen's are
1350×1688 and 1080×1920 at high motion, drawn into a 389-wide column. Video
count is not a useful lever; video weight and resolution are.

## What is left, and what it would buy

**1. The work line is printed three times.** 186 cells and 186 images on every
page, so the loop can wrap without a seam. It costs about 20MB of decoded
bitmap and 675 DOM nodes. It is *not* currently causing dropped frames — the
front page is clean — so this is a memory and load argument, not a smoothness
one. Two turns instead of three would cut a third of it. **Medium win, and it
touches the one mechanism that makes the endless scroll work, so I would not do
it without a careful look.**

**2. 209 elements carry `filter: grayscale(1)`.** Only 24–33 are on screen at
once and the compositor builds 4 layers total, so this is cheaper than it
sounds — a filter on a still element is rasterised once and cached. **Low win.**
The one case worth changing is that Sanity can desaturate server-side
(`sat=-100`), which would remove the filter *and* shrink the file — but the
cells go colour on hover, so it would mean two renditions per cell.

**3. Project pages still pull 3.2–4.5MB, mostly images.** 140 image requests on
KOJA. The strip behind the gallery is the bulk of it and the visitor cannot see
any of it. It no longer loads eagerly, but `loading="lazy"` defers nothing when
the elements sit at the height of the window — about 71 still download. Not
rendering the strip at all while a gallery covers it would stop that, at the
cost of rebuilding it when the gallery closes. **Biggest remaining win on load
time; needs care around the closing transition.**

**4. Hard flicks briefly blank a column or three in the band.** Pre-existing —
I checked production before and after, identically. It is load latency, not the
render window: widening the window did not change it. Raising `loading="eager"`
for the frames either side of the window would fix it. **Small win, low risk.**

**5. No webm.** 2 of 50 films have one. WebM would cut Chrome and Firefox bytes
on the heaviest files. **Medium win on load, none on smoothness.**

## The thing I would change about how we work

Three separate rules were keyed to something that was true when written and
quietly stopped being true: "the first project" (which became an 8-frame
launch), `near = true` (added when pages had no width, kept after they did),
and one `sizes` figure for frames of every shape. Each was correct and
commented when it was written. None had anything watching it.

The browser checks now run on a real GPU measure nothing — they assert
behaviour, not frame time. A check that scrolls a project page and fails above
a dropped-frame threshold would have caught all three within a day of each
being introduced. That is the one piece of infrastructure this session showed
we are missing.
